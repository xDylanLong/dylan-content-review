# 社媒长文的口语化编辑

适用于已有中文长文的润色，尤其是面向有专业背景读者的解释文章。目标是让作者把事情讲清楚、读者顺着读下去；保留文章的信息密度和作者判断。

## 正文段首先给结论

每个编号小点（没有编号时为独立论证段组）的第一句话直接给出具体结论、规则或判断，让读者先知道能获得什么，再解释依据、机制、后果或例子。必要条件与结论一起写清，不为抢先下结论丢掉适用范围。段首结论应由已有材料支持，不为吸引阅读夸大。

按“结论 → 解释”组织正文，不先讲故事、铺场景、提悬念，再等到段尾揭晓观点。小标题不能代替正文首句的判断。同一个小点可以分成结论、例子和解释几个短段，不要求每个换行后的自然段再造一个结论。

阅读动机来自结论本身的信息量，例如“查不到的指标必须返回 None，不能用 0 代替”。不先写“这里有个特别值得注意的细节”，也不先问“用户说第二个换掉时，会发生什么”。先说“客户端重排列表后，必须同步新顺序，否则模型可能选错商品”，再解释原因。

段落之间直接推进内容。只有条件变化或逻辑关系可能被误解时，才加简短转折；不为连贯而给每段增加过渡句。此规则适用于社媒解释长文正文，不套用口播的“常规判断 → 案例卡住 → 新判断”顺序。

## 专业科技长文的结构与版式检查

面向产品经理、开发者和架构设计者的设计经验长文，默认采用以下检查；视频和故事类文章不自动套用。creation 负责选主点与论证，本模块负责检查表达和可读性。

- **短 Hook：** 核心判断接简短概览，再进入正文；删掉 Hook 中重复展开的流程和案例。保留必要点题，不附“我重新排序了”“这次只保留”等编辑过程；不凭空造反常识。
- **标题与排序：** 主点标题让读者直接知道建议，按重要性和理解依赖推进。标题不能为了简短混淆概念，例如工具说明与工具代码不同；无依据的事实变化要指出，不静默润色过去。
- **编号解决不同问题：** 一节通常 2–3 个小点，分别解释建议、差异或决策。先摘出每点回答的问题，重复的合并；不用固定七节，不为凑三点扩写。
- **结论独立一行：** 用 `1. **具体结论。**` 等格式，解释在空行后展开。完整例子、加强前句的限制或后果可另起短段，通常每段 1–3 个完整句子；不把一句话拆成几个词组，不连续堆多行没有新增信息的金句。
- **例证支持结论：** 优先使用当前项目实例，用“例如”接入；解释动作与后果，避免含糊的“这种设计很有价值”。未给真实案例时不编造。产品架构讲职责、信息流和边界，不默认加目录树、安装或点击教程。
- **整节有取舍：** 覆盖作用、另一种做法的代价和采用条件即可，不要求每小点重复完整六步。“如何决定……？”可以直接作为决策小点标题，后面必须给答案，不加“我的标准是”。对另一种做法客观说明，不能无证据写成“现在大家都这样做”。
- **结尾能收住：** 2–3 个短段归纳关键职责和适用边界；不再铺测试表，不新增观点或宣称参考项目已生产就绪。
- **直接可发布：** 用户要成稿就只交付对应正文与必要来源，不附检测报告、模式说明和改稿历史。局部修改只交付该节，不复述全文。

### 小节形状示意（结构占位，不是事实或固定文案）

```markdown
### 一、明确的设计建议

1. **先给具体结论。**

例如……。说明这个动作为什么支持结论。

2. **另一小点回答不同的问题。**

另一种设计怎样工作、付出什么代价，本方案改变哪里。

3. **如何选择？给出判断条件。**

满足什么条件采用，哪些情况不必增加复杂度。
```

不要照抄占位句。编号结构可以一致，各小点的解释长度和材料按信息需要展开；这种有意的阅读结构不按口播的排比上限删掉。

## 改写顺序

1. **先保真。** 记住原文的主体、动作、条件、否定、范围和判断强度。保留来源链接、数字限定和技术名称；作者评价与事实分开。不要把“最完整”悄悄改成“比较完整”，也不要把“降低风险”升级为“防止”。需要事实核验或改变立场的建议单独说明。
2. **再讲顺。** 找到长句里谁做什么，把前置条件放在动作前，把结果接在动作后。把嵌套括号里的必要解释移成相邻句子。按意思拆句，同一个动作及其条件尽量放在一起，避免一句一行的碎片化。
3. **补具体关系。** “执行权、接口契约、预算口径”等抽象表达，落到原文已有的操作者、检查项或结果上。保留专业读者需要的术语，只解释影响理解的部分。同一对象接着讲，条件变化时明确用“但如果”等转折。关系已经清楚就直接接下去，不必每段加引导句。
4. **清理编辑新增的套话。** 对照原文检查自己加了什么。如果“这一条特别实用”“这里有个容易漏掉的细节”“对产品经理来说，值得借鉴的是”等句子只评价重要性，没有补信息，就删掉或并入具体解释。检查相邻小节是否都变成“评价开场—分点—总结”的同一结构，让段落在信息说完时结束。
5. **复核两遍。** 先单独读各编号小点的结论行，确认已直接给出具体判断，再读完整段落，确认解释支持判断、指代清楚、句子能自然念出；再对照原稿，确认事实、限定、观点强度和用户指定结构没有丢失。减少套话后仍然要顺，不能靠恢复原文长句来保真。

## 保留与取舍

- 小标题、表格、必要列表服务阅读；用户原有七条结构可以保留，不套口播的分点上限。
- 原文已经自然的句子可以不动。技术名词允许重复，不为避重复换成模糊近义词。
- 自然感来自准确的动作和作者已有口吻。不要新添“说白了”“你想想”“我有个毛病”等口头装饰，也不要故意写磕巴。
- 事实缺失不能靠解释补齐。异步提取不自动等于完全没有延迟，内部评测不自动等于普遍效果；原文没有给出的保证不要加。
- 默认交付完整改稿。用户只要正文就只给正文；必要的语义疑点放在正文外，简短说明，不混入作者口吻。

## 一个改写例子

原句：
> apply_change 会重新核对提案来源、当前规则和宿主批准状态，且规则是在应用那一刻重新查的。

改为：
> 执行变更前，系统必须按当前规则重新检查提案。apply_change 会核对提案从哪来、现在的规则允不允许、接入方系统有没有批准；规则在执行那一刻重新查询。

保留了执行主体、三个检查项和时间条件。后面不必再加“这个细节特别值得产品经理学习”，也不用另起一段总结执行边界。示例只展示编辑动作，不要求其他段落照套句式。
